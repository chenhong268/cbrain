# Bug #31 & #32 修复设计

> 日期：2026-05-22

## Bug #31: delete/merge 后 LanceDB 向量残留

### 问题

`PageManager.delete()` 只清 SQLite 不清 LanceDB。`merge()` 最终调 `delete()` 同理。`SyncManager.removePage()` 是对的，但 PageManager 没走那条路。

### 修复方案：构造器注入 LanceDBManager

**改动点：**

1. **`src/core/page.ts`**
   - 构造器加 `lance?: LanceDBManager`（可选参数，向后兼容）
   - `delete()` 在 `this.db.deletePageCascaded(slug)` 后加 `await this.lance?.deleteByPageSlug(slug)`
   - `delete()` 返回类型从 `boolean` 改为 `Promise<boolean>`（因为 LanceDB delete 是 async）

2. **`src/mcp/context.ts`**
   - `new PageManager(db, vaultPath, logger)` → `new PageManager(db, vaultPath, logger, lance)`

3. **调用方适配**
   - 所有调用 `page.delete()` 的地方加 `await`（MCP tools、merge 内部调用等）
   - `merge()` 本身也需改为 async

**不需要改的：**
- `merge()` 不需要额外处理——它调 `this.delete(sourceSlug)` 已经覆盖
- `SyncManager.removePage()` 已经是对的，不用动

### 测试

- 单元测试：mock LanceDBManager，验证 `delete()` 调了 `deleteByPageSlug`
- 单元测试：mock LanceDBManager，验证 `merge()` 内部 delete 清了向量

## Bug #32: watcher 无 debounce、无并发控制

### 问题

1. `syncPage` 是 fire-and-forget，50 个文件变更 = 50 个并发 LLM 调用
2. 同一 slug 上一次还没完成就可能被再次触发
3. 启动全量扫描无分批，大量文件同时压入

### 修复方案：per-slug in-flight 跟踪 + p-limit 并发队列 + 启动分批

**新增依赖：** `p-limit`（轻量并发控制库，~50 行源码）

**改动点（全在 `src/core/maintenance/watcher.ts`）：**

1. **并发队列**
   - `p-limit(3)` 限制同时最多 3 个 syncPage 在跑
   - syncPage 通过 `limit(() => this.sync.syncPage(...))` 入队

2. **per-slug in-flight 跟踪**
   - 新增 `private inFlight = new Set<string>()`
   - syncPage 开始前检查 slug 是否在 inFlight 中，在就跳过
   - 开始时 `inFlight.add(slug)`，完成/失败时 `inFlight.delete(slug)`

3. **启动分批**
   - 首次 scan 检测到超过 10 个变更文件时，按每批 10 个分组
   - 每批提交后 `await new Promise(r => setTimeout(r, 500))` 留间隔
   - 后续常规 scan 不分批（变更量通常很小）

### 改动后的核心逻辑

```ts
import pLimit from "p-limit";

export class FileWatcher {
  private limit = pLimit(3);
  private inFlight = new Set<string>();
  private isFirstScan = true;

  // syncPage 入口
  private enqueueSync(slug: string): void {
    if (this.inFlight.has(slug)) {
      this.logger?.info("watcher", "跳过：正在同步", { slug });
      return;
    }
    this.inFlight.add(slug);
    this.limit(() => this.sync.syncPage(slug, this.vaultPath))
      .then(() => { this.logger?.info("watcher", "同步完成", { slug }); })
      .catch((e) => { this.logger?.warn("watcher", `同步失败: ${slug}`, { error: String(e) }); })
      .finally(() => { this.inFlight.delete(slug); });
  }

  // doScan 中分批提交
  // 首次 scan: 收集所有变更，按 10 个一批提交，批间 sleep 500ms
  // 后续 scan: 直接提交（量小）
}
```

### 测试

- 单元测试：mock SyncManager，验证同一 slug 第二次 enqueueSync 被跳过
- 单元测试：验证并发上限（提交 10 个 slug，同时只有 3 个在跑）
- 单元测试：验证首次 scan 分批行为

## 风险

- `delete()` 改 async 是 breaking change，需确认所有调用方都加 await
- `p-limit` 是新依赖，需确认兼容 Bun runtime（已验证：p-limit 是纯 JS，无 native 依赖）
