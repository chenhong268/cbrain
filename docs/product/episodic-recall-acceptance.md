# Episodic Recall — 自然对话验收标准

> 验收 #85/#86 的"忘名情境找人"能力。防止路由或 Agent 协议漂移。

## 适用范围

用户**不记得人名**，但记得时间、地点、事件、主题、关系等情境线索，期望 Agent 推荐候选人。

## 触发条件

| 类型 | 信号 | 示例 |
|:-----|:-----|:-----|
| 强触发 | 那个人是谁、叫什么来着、想不起名字、忘了名字 | "那个人叫什么来着" |
| 条件触发 | 时间/地点/事件/场景/主题 + 见过/认识/遇到/一起做过 + 谁/那个人/人 | "去年团建见过谁" |

**不适用**（应走 query 或 connect）：

- 用户提到具体人名（"人物A认识谁"）
- 纯关系查询（"人物A和人物B什么关系"）
- 已知实体的信息查询（"组织F团队的人"）

## 正确回答形态

Agent 调用 `recall_episode` 后的回答应包含：

1. **候选人列表**：按匹配分数排序，最多 5 人
2. **匹配线索**：说明每个候选人在哪些维度匹配（时间/主题/事件/场景/关系）
3. **紧凑证据**：每个候选人附 1-2 条简短证据摘录（≤ 200 字）
4. **澄清线索**（可选）：当候选人多于 1 个且分数接近时，附一条下一步可问的澄清问题

回答格式示例：

```text
找到 2 位可能的候选人：

1. 人物A（匹配度：高）
   - 线索：时间（去年）+ 场景（团建）
   - 证据：人物A参加去年团建活动

2. 人物B（匹配度：中）
   - 线索：场景（团建）
   - 证据：人物B和组织F有团建记录

你想确认的是其中哪位？
```

## 禁止行为

| 禁止 | 原因 |
|:-----|:-----|
| 泛搜索结果倾倒（列出所有相关页面） | 用户找人，不是搜文档 |
| 主动建议联系某人 | Agent 不应替用户决定社交行为 |
| 暴露工具细节（工具名、参数、JSON） | 用户不需要知道调了 recall_episode |
| 把候选人当事实说 | 必须标注"可能/待确认" |
| 返回空结果时沉默 | 必须给出诊断解释（扫描了多少人、哪些线索无匹配） |
| 使用真实人名/公司名 | 所有示例必须匿名化 |

## 路由 Eval 用例

完整 eval 位于 `skills/episodic.routing-eval.jsonl`（14 条：8 正例 + 6 反例）。

正例应触发 `query.md [episodic]` → `recall_episode`：

| # | 输入 | 触发原因 |
|---|------|---------|
| 1 | 去年团建见过谁 | 时间+场景+见过+谁 |
| 2 | 那个人叫什么来着 | 强触发 |
| 3 | 上个月聚餐认识的那个人 | 时间+场景+认识+那个人 |
| 4 | 项目上线一起干的人是谁 | 事件+一起干+的人 |
| 5 | 想不起名字了，就是在某次技术分享上认识的 | 强触发+场景线索 |
| 6 | 在地点E的那次会议上遇到过谁 | 地点+事件+遇到+谁 |
| 7 | 主题C相关的项目里认识的人有哪些 | 主题+认识+谁 |
| 8 | 忘了名字，就是和人物A一起做过事件的那个 | 强触发+关系线索 |

反例**不应**触发 episodic：

| # | 输入 | 应走路由 | 原因 |
|---|------|---------|------|
| 1 | 人物A认识谁 | query | 提到具体人名 |
| 2 | 人物A和人物B什么关系 | connect | 纯关系查询 |
| 3 | 组织F团队的人 | query | 已知实体信息查询 |
| 4 | 见过谁 | query | 无情境线索，太宽泛 |
| 5 | 当时怎么设计的 | deep_recall | 内容回忆意图 |
| 6 | 讨论过吗 | deep_recall (grounded) | 核查确认意图 |
